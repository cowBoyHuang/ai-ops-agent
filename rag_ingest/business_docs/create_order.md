# 整体生单请求业务流程说明（业务模块级）

> 文档说明：按段落语义整理，标题为内容摘要。

## 流程总览：端到端生单主链路

生单请求从接入层进入后，会先完成请求治理与校验，再进入路由判定层，随后分流到普通生单或拼接生单路径。两条路径最终都会进入生单编排与子单执行，再进行结果修复与汇总，最后完成监控上报与消息通知并返回结果。

## 业务流程图：模块串联路径

客户端请求 -> 接入层（新聚合入口 / 老PC无线入口） -> 请求治理层（参数校验、请求修正、敏感信息处理） -> 路由判定层（普通生单 / 拼接生单） -> 生单处理层（普通处理器 / 拼接处理器） -> 生单编排层（BookingTag与价格准备、依赖计算） -> 子单业务执行层（机票主单、红包、辅营、营销、会员、酒店、服务费） -> 结果修复与汇总层（主单回填、失败容忍、错误提示聚合） -> 后置运营层（监控、日志、消息、风控缓存） -> 返回生单结果

## 接入层：承接不同来源的生单请求

接入层负责承接不同来源的生单请求，包括新聚合接口与历史PC/无线接口。该层主要做协议适配、请求接入统一化和基础上下文准备，保证后续业务模块处理同一类业务语义。

## 请求治理层：生单前的基础治理动作

请求治理层负责生单前的基础治理动作，包括参数完整性校验、业务字段合法性校验、请求结构修正、联系人与乘机人等敏感字段加密处理，以及必要的前置缓存触发。该层的目标是让后续模块拿到可执行、可追踪、可审计的标准请求。

## 路由判定层：链路与处理器

路由判定层根据航程类型、乘机人结构、多报价信息、客户端控制参数等条件，判断请求应走普通生单路径还是拼接生单路径。该层本质上是策略分流中心，决定后续处理链路与处理器。

## 普通生单处理层：执行生单主流程

普通生单处理层在非拼接场景下负责执行生单主流程，包括参数模型转换、特殊场景拦截检查、调用生单管理器发起实际业务生单、并将底层结果转换为对外统一的生单响应模型。

## 拼接生单处理层：参数适配与前置规则校验

拼接生单处理层在拼接或多报价场景下负责参数适配、前置规则校验、按规则拆分子请求并行生单、以及子单结果汇总。该层重点解决合单拆分、特殊产品、多报价提示与继续生单等复杂流程控制。

## 生单编排层：组织生单执行上下文

生单编排层负责组织生单执行上下文，核心包括 BookingTag 与价格信息准备、子单创建参数构建、子单依赖关系计算、执行批次划分。该层的目标是确保各类子单按可并行且满足依赖的方式执行。

## 子单业务执行层：实际创建主单与各类子单

子单业务执行层负责实际创建主单与各类子单，包括机票主单、红包、辅营、营销、会员、酒店、服务费等。各子单模块根据自身规则决定是否生单、如何生单、失败是否可容忍，以及对主单的影响范围。

## 结果修复与汇总层：把子单结果回填到主单视图

结果修复与汇总层负责把子单结果回填到主单视图，统一处理部分失败容忍、阻断失败、错误文案聚合、金额与展示信息修复，并产出最终对外可消费的生单结果。该层决定用户最终看到的成功或失败状态和提示信息。

## 后置运营层：生单结束后的运营动作

后置运营层负责生单结束后的运营动作，包括监控埋点、日志追踪、异步消息通知、QLibra 上报、风控缓存等。该层不改变核心业务结果，但对稳定性、可观测性、风控与后续联动能力至关重要。
